O Casthop é um estúdio de transmissão ao vivo de código aberto que roda no navegador. Você entra como anfitrião, manda um link para os convidados, coloca até seis pessoas no palco e envia um único vídeo mixado para vários sites de streaming ao mesmo tempo. Uma gravação fica guardada.

Esta página coloca tudo para rodar em uma máquina Linux em cerca de dez minutos. Nada aqui exige conta paga. Os "sites de streaming" são servidores de teste locais, então você pode transmitir sem tocar no YouTube.

## O que você precisa

- **Linux** com Docker e Docker Compose. No macOS e no Windows há passos extras, veja [Docker Desktop](#docker-desktop-macos-e-windows).
- **[Bun](https://bun.com) 1.4.5 ou mais novo.** Bun é o runtime de JavaScript e o gerenciador de pacotes que este repositório usa. Não use npm.
- **Chrome ou outro navegador Chromium** para abrir o estúdio.

Você não precisa de Rust. O arquivo WebAssembly compilado já está no repositório.

## Início rápido

Rode cada passo na raiz do [repositório do Casthop](https://github.com/casthop/casthop).

**1. Baixe o código.**

```bash
git clone https://github.com/casthop/casthop.git
cd casthop
```

**2. Copie as configurações de exemplo.**

```bash
cp .env.example .env
cp .dev.vars.example .dev.vars
```

O `.env` é lido pelo Docker. O `.dev.vars` é lido pelo servidor do app. Os dois são ignorados pelo git, e os valores padrão funcionam sem mudança.

**3. Crie as pastas das gravações.**

```bash
mkdir -p data/recordings data/rtmp && chmod 777 data/recordings
```

O gravador roda como outro usuário dentro do Docker, por isso precisa de permissão de escrita em `data/recordings`.

**4. Suba os servidores de mídia.**

```bash
docker compose up -d
docker compose ps
```

Você deve ver quatro serviços rodando: `redis`, `livekit`, `egress` e `mediamtx`. O LiveKit leva áudio e vídeo entre os navegadores. O Egress mixa o palco em um único vídeo e o envia. O MediaMTX faz o papel de YouTube, LinkedIn e X. O Redis deixa o LiveKit e o Egress conversarem.

Na primeira vez, as imagens são baixadas, o que pode levar alguns minutos.

**5. Instale e inicie o app.**

```bash
bun install
bun run dev
```

Você deve ver `Local: http://127.0.0.1:5173/`. Deixe este terminal aberto. O app só escuta em `127.0.0.1`, então outras máquinas da sua rede não conseguem acessá-lo.

**6. Confira se está tudo certo.**

Em um segundo terminal:

```bash
curl http://127.0.0.1:5173/api/health
```

Você deve ver `{"ok":true,"livekit":{"ok":true},"maxOnStage":6}`. Se `ok` for `false`, o app não consegue falar com o LiveKit. Veja [Solução de problemas](#solução-de-problemas).

## Sua primeira transmissão

1. Abra [http://127.0.0.1:5173](http://127.0.0.1:5173) e digite seu e-mail.
2. No ambiente local, nenhum e-mail é enviado. O link de login aparece no terminal em que roda `bun run dev`, depois de `[casthop mail]`. Abra o link e clique em **Sign in**.
3. Dê um título ao estúdio e clique em **Open studio**.
4. Copie o link de convidado e abra em outra janela do navegador, ou envie para alguém. Convidados não precisam de conta. Veja [Convidados](/docs/guests).
5. Coloque o convidado no palco. Cabem até seis pessoas.
6. Clique em **Go live**, escolha os destinos e confirme. O indicador mostra **Starting** e vira **Live** quando o vídeo realmente está passando. Cada destino mostra o próprio status.

Para ver o que foi enviado, rode `ffprobe rtmp://127.0.0.1:1935/live/youtube`. A gravação é salva em `data/recordings/`. Veja [Destinos](/docs/destinations).

## Extras opcionais

Tudo isso fica desligado até você definir em `.dev.vars` e reiniciar o `bun run dev`. Cada item é explicado em [Configuração](/docs/configuration).

- **Login com GitHub:** `GITHUB_CLIENT_ID` e `GITHUB_CLIENT_SECRET`.
- **Chat do YouTube no estúdio:** `YOUTUBE_API_KEY` mais `YOUTUBE_LIVE_CHAT_ID` ou `YOUTUBE_VIDEO_ID`. Defina `YOUTUBE_CHAT_STUDIO_ID` com o estúdio que deve mostrá-lo.
- **Chat da Twitch e do Kick:** `TWITCH_CHANNEL` e `KICK_CHATROOM_ID`.
- **Link de login no navegador em vez do terminal**, para testes e `bun run measure`: `CASTHOP_DEV_LOGIN=1`.

## Solução de problemas

**`permission denied while trying to connect to the Docker daemon socket`**
Seu usuário não está no grupo `docker`. Rode `sudo usermod -aG docker $USER` e saia e entre de novo na sessão, ou coloque `sudo` na frente dos comandos do Docker.

**`Port 5173 is already in use`**
Outro servidor de desenvolvimento está rodando. Pare-o, ou encontre-o com `ss -ltnp | grep 5173`. O Casthop não escolhe outra porta, porque o gravador espera a `5173`.

**O health mostra `"ok":false`**
O LiveKit não está rodando ou não está acessível. Confira `docker compose ps` e `docker compose logs livekit`. A porta `7880` precisa estar livre.

**`Refusing default LiveKit devkey/secret outside local loopback`**
Você apontou o app para um servidor LiveKit que não está em `127.0.0.1` e ainda usa as chaves públicas de teste. Gere chaves de verdade (veja [Self-hosting](/docs/self-hosting)) e coloque em `.dev.vars`.

**Nenhum link de login**
Olhe no terminal do `bun run dev`, não na sua caixa de entrada. Se você pediu links muitas vezes, o login fica pausado por alguns minutos (a cada 15 minutos: 5 pedidos por rede, 3 links por e-mail).

**Preso em Starting**
O Egress não conseguiu abrir a página do estúdio ou chegar ao MediaMTX. Confira `docker compose logs egress`. Veja se o `bun run dev` continua rodando e se `data/recordings` tem permissão de escrita.

**Sem câmera na máquina**
O Casthop usa uma imagem de teste e áudio silencioso, então um servidor ou uma VM ainda consegue entrar. Você também pode abrir o Chrome com `--use-fake-device-for-media-stream`.

**O Bun avisa sobre a versão**
Rode `bun upgrade`. O repositório espera Bun 1.4.5 ou mais novo.

## Docker Desktop (macOS e Windows)

O arquivo compose usa host networking, que só funciona no Linux. No Docker Desktop:

- remova `network_mode: host` de cada serviço,
- publique `127.0.0.1:7880-7882`, `127.0.0.1:1935`, `127.0.0.1:8888`, `127.0.0.1:6379` e `127.0.0.1:9090`,
- defina `rtc.node_ip` do LiveKit como `host.docker.internal`,
- aponte o `ws_url` do Egress e o Redis para `host.docker.internal`.

O vídeo no navegador da mesma máquina ainda pode ficar instável assim. Por enquanto, o Linux é o caminho suportado.
