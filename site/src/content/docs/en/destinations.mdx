A destination is a streaming address (an RTMP or RTMPS URL) such as the ingest URL YouTube gives you. Casthop mixes the stage once and sends it to every destination you turn on.

## Wide and vertical

Each destination is either **16:9** (the normal wide video) or **9:16** (a tall video with cameras stacked, for TikTok, YouTube Shorts or Instagram Reels). Destinations with the same shape share one encode. Vertical gets its own encode on the server, so guests still only send their camera once.

9:16 needs the Casthop mixing page (`EGRESS_TEMPLATE_URL`) to be set.

## Local test servers

Out of the box, the destinations point at MediaMTX on your machine, standing in for YouTube, LinkedIn and X:

| Destination | Address | Check it |
|---|---|---|
| YouTube stand-in | `rtmp://127.0.0.1:1935/live/youtube` | `ffprobe rtmp://127.0.0.1:1935/live/youtube` |
| LinkedIn stand-in | `rtmp://127.0.0.1:1935/live/linkedin` | same, with `/live/linkedin` |
| X stand-in | `rtmp://127.0.0.1:1935/live/x` | same, with `/live/x` |

## Real destinations

Each studio owner adds real addresses in the **Destinations** panel, up to 16 per studio. Casthop only accepts `rtmp:` and `rtmps:` addresses, and refuses private network addresses such as `10.x` or `192.168.x`.

Do not put real stream keys in the `RTMP_*` settings. New studios copy those only when they point at `127.0.0.1`.

## Status and recovery

Each destination shows its own status: `connecting`, `live`, `retrying` or `failed`. The studio pill stays on **Starting** until video is really flowing, then shows **Live**.

If the mixer crashes or a stream drops, the studio retries on its own, waiting longer each time. On a server this needs the LiveKit webhook, see [Self-hosting](/docs/self-hosting).

## Recordings

| Where | What |
|---|---|
| `data/recordings/` | MP4 of the mixed show, written by Egress. |
| `data/rtmp/` | What the local MediaMTX received. |
| `RECORDINGS` (R2) | Per-person tracks, when **Separate recordings** is on. |

To check that a recording has sound: `bash scripts/check-silent-audio.sh data/recordings/<file>.mp4`.

## Separate recordings (per-person tracks)

Turn on **Separate recordings** in the Go live dialog before you go live. Each person on stage then records their own camera and mic in their browser and uploads it in 2-second pieces during the show. A closed tab only loses the last piece. Only people on stage record. Guests backstage do not.

After the show, open **Recordings** in the studio to download each track. Files are WebM, or MP4 from Safari.

## Replays

Turn the mixed MP4 into a replay with the Rust helper:

```bash
cargo run -p casthop-post -- inspect data/recordings/<file>.mp4
cargo run -p casthop-post -- hls data/recordings/<file>.mp4 /tmp/replay-hls
```

Then, signed in as the owner or a co-host, upload it with `POST /api/studios/:id/replays` and set `visibility` to `private` or `public`. Private replays show on your studio list only. Public replays play at `/watch/:id`.

## Clips

While you are live, press **Clip** (or the C key) to save the last 30 or 60 seconds. Clips appear next to the replays with a download link and follow the same private and public rules.

## Chat

People in the studio can chat with each other. While you are live, comments from YouTube, Twitch and Kick can join the same panel. Hosts and co-hosts can pin one comment onto the video.

- **YouTube:** set `YOUTUBE_API_KEY` plus `YOUTUBE_LIVE_CHAT_ID` or `YOUTUBE_VIDEO_ID`, or the three `YOUTUBE_OAUTH_*` values to find your own active broadcast. Set `YOUTUBE_CHAT_STUDIO_ID` to the studio that should show it.
- **Twitch:** set `TWITCH_CHANNEL` to the channel name.
- **Kick:** set `KICK_CHATROOM_ID` to the chatroom number.

Unset means that source stays hidden. Nothing breaks. Comments are only read while you are live, and they are not saved with the replay. X chat is not supported because X has no free chat API. LinkedIn comments need a partner API and are not supported. See [Configuration](/docs/configuration).

## Who sees what

- **Owners and co-hosts** receive full destination URLs when signed in (session cookie).
- **Guests and public requests** get a masked suffix only, and a `hasKey` flag. This applies to `GET /api/studios/:id` and the WebSocket `state` frame.
- Stream keys are stored in Durable Object storage, not in the repo.
