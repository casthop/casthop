A destination is an RTMP URL. Each destination picks **16:9** (the program) or **9:16** (a second stacked composite). Destinations that share an aspect share one Egress encode.

## Local stand-ins

Out of the box, the destinations are MediaMTX stand-ins for YouTube, LinkedIn and X:

| Destination | Ingest | Watch |
|---|---|---|
| YouTube stand-in | `rtmp://127.0.0.1:1935/live/youtube` | `ffprobe rtmp://127.0.0.1:1935/live/youtube` |
| LinkedIn stand-in | `rtmp://127.0.0.1:1935/live/linkedin` | same, `/live/linkedin` |
| X stand-in | `rtmp://127.0.0.1:1935/live/x` | same, `/live/x` |

## Real destinations

For production, replace these with real YouTube, LinkedIn and X ingest URLs. Casthop validates destinations: only `rtmp:` URLs are accepted from clients, and private-network (RFC 1918) targets are rejected.

## Status, Live, and recovery

Each destination row shows its own RTMP status (`connecting`, `live`, `retrying`, `failed`). The Destinations panel also shows 16:9 and 9:16 output status separately. The studio Live pill stays on Starting until Egress is producing: stream bytes or duration, or a short settle after RTMP `started_at`. It does not flip to Live just because the compositor process exists.

Mark a destination 9:16 for TikTok, YouTube Shorts, or Instagram Reels ingest. The 16:9 layout (solo / side / screen) is unchanged. Vertical uses its own stacked-camera layout with a captions band. Guests still publish once.

If Egress or a stream drops, the studio retries with backoff. This relies on signed LiveKit webhooks, see [Self-hosting](/docs/self-hosting).

## Recordings

| Where | What |
|---|---|
| `data/recordings/` | Egress MP4 of the composite. |
| `data/rtmp/` | MediaMTX fMP4 from the local RTMP edge. |

Inspect a recording with the Rust helper:

```bash
cargo run -p casthop-post -- inspect data/recordings/<file>.mp4
```

To check that a recording is not silent, run `bash scripts/check-silent-audio.sh data/recordings/<file>.mp4`.

## Chat

People in the studio can send comments in the room. While the show is live, Casthop can also poll YouTube Live chat (`liveChatMessages.list`) and merge those comments into the same panel. Hosts and co-hosts can pin one comment onto the compositor overlay (Canvas2D lower-third stack). Polling uses the API’s `pollingIntervalMillis`. Unset credentials hide YouTube ingest; the studio does not error.

Need Worker secrets: `YOUTUBE_API_KEY` plus `YOUTUBE_LIVE_CHAT_ID` or `YOUTUBE_VIDEO_ID`, or the OAuth refresh trio (`YOUTUBE_OAUTH_CLIENT_ID`, `YOUTUBE_OAUTH_CLIENT_SECRET`, `YOUTUBE_OAUTH_REFRESH_TOKEN`) which looks up the owner’s active broadcast. See [Configuration](/docs/configuration).

X’s API requires a paid tier. LinkedIn live comments need a partner API. Neither is wired. There is no VOD / replay of destination chat; polling runs only while the studio is live. The YouTube page-token cursor stays in Durable Object storage and is never sent to guests or public GET / WebSocket state.

## Who sees what

- **Owners and co-hosts** receive full destination URLs when signed in (session cookie).
- **Guests and public requests** get a masked suffix only, and a `hasKey` flag. This applies to `GET /api/studios/:id` and the WebSocket `state` frame.
- Stream keys are stored in Durable Object storage, not in the repo.
