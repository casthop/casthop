## Navigateur

L’interface est en TypeScript. Les chemins média critiques sont en Rust compilé en WebAssembly dans `crates/casthop-media`, sans import JS, ce qui permet de l’utiliser dans un AudioWorklet.

- **Audio :** la suppression de bruit RNNoise et la VAD/les indicateurs de niveau tournent dans un AudioWorklet avant que le micro soit publié vers LiveKit. `?fx=js` ou `?fx=off` permet de comparer.
- **Disposition et composition :** WASM calcule la disposition. Le compositeur en direct est du Canvas2D dans un Worker dédié avec OffscreenCanvas quand WebCodecs est disponible (`?thread=main` force l’ancien chemin sur le thread principal). `?compose=wasm` est le blit CPU, `?compose=webgpu` le chemin GPU en Rust, `?compose=webgpu-ts` le chemin GPU en TypeScript. Canvas2D reste le défaut ; le GPU n’a pas gagné au banc d’essai.
- **Flou de la caméra :** utilise MediaPipe Selfie Segmenter. `@mediapipe/tasks-vision` et son modèle ne se chargent que si le flou est activé, depuis cette origine, sans CDN.

Le job CI `perf` compare le compositeur main et worker dans Chrome (`PERF=1 bun run test:perf`). Les chiffres : [`MEASUREMENTS.md`](https://github.com/casthop/casthop/blob/main/MEASUREMENTS.md).

## LiveKit reste le SFU

LiveKit (Go) est déjà le chemin rapide, donc Casthop ne le remplace pas. Les navigateurs publient en simulcast WebRTC, et Egress s’abonne en pleine qualité.

## Pourquoi la diffusion multiple via Egress

Cloudflare Stream Live exige un compte Cloudflare avec Stream activé, et le stockage Stream est prépayé. Ce prototype ne souscrit pas de service payant. Egress transcode déjà une seule fois et peut émettre plusieurs URL RTMP à partir de cet unique encodage : c’est la voie de l’auto-hébergement. Un Casthop hébergé pourrait encore envoyer un seul flux RTMP vers Stream plus tard, si le calcul de diffusion y gagne. Voir [`MEASUREMENTS.md`](https://github.com/casthop/casthop/blob/main/MEASUREMENTS.md) dans le dépôt.

## Plan de contrôle

L’application est un Worker Hono avec un Durable Object par studio (scène, disposition, chat, destinations) et D1 pour l’index des studios. R2 stocke les replays HLS, les clips en direct et les morceaux ISO par personne envoyés par chaque navigateur pendant un show. Egress écrit toujours le MP4 source sur le volume des enregistrements ; `casthop-post hls` le package et le Worker le sert. Les endpoints chauds du Worker restent en TypeScript ; un portage workers-rs a été mesuré (`bun run bench:worker`) et n’a gagné ni sur le CPU, ni sur le démarrage à froid, ni sur la taille du bundle.

## Chat des destinations

En direct, le Durable Object du studio lit le chat YouTube (`liveChatMessages.list`), Twitch et Kick quand leurs réglages sont présents (`worker/chat-ingest.ts`, `worker/chat-platforms.ts`). Les commentaires rejoignent la liste du chat de la salle. Les hôtes et les co-hôtes peuvent en épingler un sur l’overlay Canvas2D. Le curseur de sondage YouTube est exclu de l’état public du studio. X et LinkedIn ne sont pas lus.

## Pastille Live

La pastille du studio n’est `live` que lorsqu’Egress produit de la sortie : octets ou durée de stream, ou un court délai de stabilisation après le `started_at` RTMP (LiveKit peut signaler un démarrage avant que MediaMTX ait le stream). D’ici là, la pastille reste sur Starting. Si le Chrome du compositeur meurt, le heartbeat retire Live et le studio réessaie avec un backoff.

## casthop-post

`crates/casthop-post` inspecte, remuxe et package le HLS pour le lecteur de replays R2. `clip` copie les N dernières secondes d’un dossier packagé. Voir [Destinations](/docs/destinations).
