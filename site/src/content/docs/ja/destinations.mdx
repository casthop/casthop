配信先とは、YouTube が発行するインジェスト URL のような、配信用のアドレス（RTMP または RTMPS の URL）のことです。Casthop はステージを 1 回だけミックスし、オンにしたすべての配信先へ送ります。

## 横長と縦長

配信先は、**16:9**（ふつうの横長の映像）か **9:16**（カメラを縦に並べた縦長の映像。TikTok、YouTube Shorts、Instagram Reels 向け）のどちらかです。同じ形の配信先は、1 回のエンコードを共有します。縦長はサーバー側で別にエンコードするので、ゲストがカメラ映像を送るのは今までどおり 1 回だけです。

9:16 を使うには、Casthop のミックス用ページ（`EGRESS_TEMPLATE_URL`）の設定が必要です。

## ローカルのテスト用サーバー

初期状態では、配信先は手元のマシンの MediaMTX を指します。YouTube、LinkedIn、X の代わりです。

| 配信先 | アドレス | 確認方法 |
|---|---|---|
| YouTube の代替 | `rtmp://127.0.0.1:1935/live/youtube` | `ffprobe rtmp://127.0.0.1:1935/live/youtube` |
| LinkedIn の代替 | `rtmp://127.0.0.1:1935/live/linkedin` | 同じ。`/live/linkedin` にします |
| X の代替 | `rtmp://127.0.0.1:1935/live/x` | 同じ。`/live/x` にします |

## 本物の配信先

スタジオのオーナーは、**Destinations** パネルで本物のアドレスを追加します。1 つのスタジオに最大 16 件です。Casthop が受け付けるのは `rtmp:` と `rtmps:` のアドレスだけで、`10.x` や `192.168.x` のようなプライベートネットワークのアドレスは拒否します。

`RTMP_*` の設定に本物のストリームキーを入れないでください。新しいスタジオは、これらが `127.0.0.1` を指しているときだけコピーします。

## 状態と復旧

配信先ごとに、`connecting`、`live`、`retrying`、`failed` のいずれかの状態が表示されます。スタジオのステータス表示は、映像が実際に流れ始めるまで **Starting** のままで、流れ始めると **Live** になります。

ミキサーがクラッシュしたり、配信が途切れたりすると、スタジオは待ち時間を少しずつ延ばしながら自動で再試行します。サーバーでは、LiveKit の webhook が必要です。[セルフホスト](/docs/self-hosting) を見てください。

## 録画

| 場所 | 内容 |
|---|---|
| `data/recordings/` | Egress が書き込む、ミックスしたショーの MP4。 |
| `data/rtmp/` | ローカルの MediaMTX が受け取ったもの。 |
| `RECORDINGS` (R2) | **Separate recordings** がオンのときの、個人別のトラック。 |

録画に音が入っているか確認するには、`bash scripts/check-silent-audio.sh data/recordings/<file>.mp4` を実行します。

## 個別録画（個人別トラック）

ライブを始める前に、Go live ダイアログで **Separate recordings** をオンにします。すると、ステージにいる各人が、自分のカメラとマイクをそれぞれのブラウザで録画し、ショーの間に 2 秒ごとの断片としてアップロードします。タブが閉じられても、失われるのは最後の断片だけです。録画するのはステージにいる人だけで、バックステージのゲストは録画しません。

ショーのあと、スタジオの **Recordings** を開くと、各トラックをダウンロードできます。ファイルは WebM で、Safari の場合は MP4 です。

## リプレイ

ミックスした MP4 は、Rust 製のツールでリプレイにできます。

```bash
cargo run -p casthop-post -- inspect data/recordings/<file>.mp4
cargo run -p casthop-post -- hls data/recordings/<file>.mp4 /tmp/replay-hls
```

そのあと、オーナーか共同ホストとしてサインインした状態で、`POST /api/studios/:id/replays` でアップロードし、`visibility` を `private` か `public` にします。非公開のリプレイは、自分のスタジオ一覧にだけ表示されます。公開のリプレイは `/watch/:id` で再生されます。

## クリップ

ライブ中に **Clip**（または C キー）を押すと、直前の 30 秒か 60 秒を保存できます。クリップはリプレイの隣に、ダウンロードリンク付きで表示され、非公開と公開のルールもリプレイと同じです。

## チャット

スタジオにいる人どうしで、チャットができます。ライブ中は、YouTube、Twitch、Kick のコメントも同じパネルに表示できます。ホストと共同ホストは、コメントを 1 件、映像にピン留めできます。

- **YouTube:** `YOUTUBE_API_KEY` と、`YOUTUBE_LIVE_CHAT_ID` または `YOUTUBE_VIDEO_ID` を設定します。または、3 つの `YOUTUBE_OAUTH_*` の値を設定すると、自分の進行中のライブ配信を探します。 表示するスタジオを `YOUTUBE_CHAT_STUDIO_ID` に設定します。
- **Twitch:** `TWITCH_CHANNEL` にチャンネル名を設定します。
- **Kick:** `KICK_CHATROOM_ID` にチャットルーム番号を設定します。

未設定の場合、そのソースは表示されません。何も壊れません。コメントを読み取るのはライブ中だけで、リプレイには保存されません。X には無料のチャット API がないため、X のチャットは非対応です。LinkedIn のコメントにはパートナー API が必要で、非対応です。[設定](/docs/configuration) を見てください。

## 誰に何が見えるか

- **オーナーと共同ホスト**は、サインイン中（セッション Cookie）に、配信先の完全な URL を受け取ります。
- **ゲストと公開リクエスト**には、マスクされた末尾と `hasKey` フラグだけが渡されます。これは `GET /api/studios/:id` と、WebSocket の `state` フレームに当てはまります。
- ストリームキーは、リポジトリではなく Durable Object のストレージに保存されます。
