Casthop ist ein Open-Source-Livestudio, das im Browser läuft. Du meldest dich als Host an, schickst Gästen einen Link, holst bis zu sechs Leute auf die Bühne und sendest ein gemischtes Video gleichzeitig an mehrere Streaming-Seiten. Eine Aufnahme bleibt erhalten.

Diese Seite bringt es in etwa zehn Minuten auf einem Linux-Rechner zum Laufen. Du brauchst dafür kein Bezahlkonto. Die „Streaming-Seiten“ sind lokale Testserver, du kannst also live gehen, ohne YouTube anzufassen.

## Was du brauchst

- **Linux** mit Docker und Docker Compose. Für macOS und Windows brauchst du zusätzliche Schritte, siehe [Docker Desktop](#docker-desktop-macos-und-windows).
- **[Bun](https://bun.com) 1.4.5 oder neuer.** Bun ist die JavaScript-Runtime und der Paketmanager dieses Repos. Nutze kein npm.
- **Chrome oder einen anderen Chromium-Browser**, um das Studio zu öffnen.

Du brauchst kein Rust. Die kompilierte WebAssembly-Datei liegt im Repo.

## Schnellstart

Führe jeden Schritt im Hauptordner des [Casthop-Repos](https://github.com/casthop/casthop) aus.

**1. Hol dir den Code.**

```bash
git clone https://github.com/casthop/casthop.git
cd casthop
```

**2. Kopiere die Beispiel-Einstellungen.**

```bash
cp .env.example .env
cp .dev.vars.example .dev.vars
```

`.env` liest Docker. `.dev.vars` liest der App-Server. Beide stehen in der `.gitignore`, und die Standardwerte passen so.

**3. Lege die Ordner für Aufnahmen an.**

```bash
mkdir -p data/recordings data/rtmp && chmod 777 data/recordings
```

Der Recorder läuft in Docker unter einem anderen Nutzer und braucht deshalb Schreibrechte auf `data/recordings`.

**4. Starte die Medienserver.**

```bash
docker compose up -d
docker compose ps
```

Du solltest vier laufende Dienste sehen: `redis`, `livekit`, `egress` und `mediamtx`. LiveKit schickt Audio und Video zwischen den Browsern hin und her. Egress mischt die Bühne zu einem Video und sendet es raus. MediaMTX steht für YouTube, LinkedIn und X. Über Redis sprechen LiveKit und Egress miteinander.

Beim ersten Start lädt Docker die Images herunter. Das kann ein paar Minuten dauern.

**5. Installiere und starte die App.**

```bash
bun install
bun run dev
```

Du solltest `Local: http://127.0.0.1:5173/` sehen. Lass dieses Terminal offen. Die App lauscht nur auf `127.0.0.1`, andere Rechner in deinem Netz kommen also nicht heran.

**6. Prüfe, ob alles läuft.**

In einem zweiten Terminal:

```bash
curl http://127.0.0.1:5173/api/health
```

Du solltest `{"ok":true,"livekit":{"ok":true},"maxOnStage":6}` sehen. Ist `ok` auf `false`, erreicht die App LiveKit nicht. Siehe [Fehlerbehebung](#fehlerbehebung).

## Dein erster Stream

1. Öffne [http://127.0.0.1:5173](http://127.0.0.1:5173) und gib deine E-Mail-Adresse ein.
2. Lokal wird keine E-Mail verschickt. Den Anmeldelink druckt das Terminal, in dem `bun run dev` läuft, unter `[casthop mail]`. Öffne ihn und klick auf **Sign in**.
3. Gib dem Studio einen Titel und klick auf **Open studio**.
4. Kopiere den Gastlink und öffne ihn in einem zweiten Browserfenster, oder schick ihn jemandem. Gäste brauchen kein Konto. Siehe [Gäste](/docs/guests).
5. Hol den Gast auf die Bühne. Bis zu sechs Leute können auf der Bühne sein.
6. Drück **Go live**, wähl Ziele und bestätige. Die Anzeige zeigt **Starting** und wechselt zu **Live**, sobald wirklich Video fließt. Jedes Ziel zeigt seinen eigenen Status.

Um zu sehen, was rausgegangen ist, führ `ffprobe rtmp://127.0.0.1:1935/live/youtube` aus. Die Aufnahme landet in `data/recordings/`. Siehe [Ziele](/docs/destinations).

## Optionale Extras

Alles davon ist aus, bis du es in `.dev.vars` setzt und `bun run dev` neu startest. Jedes Extra ist in [Konfiguration](/docs/configuration) erklärt.

- **GitHub-Anmeldung:** `GITHUB_CLIENT_ID` und `GITHUB_CLIENT_SECRET`.
- **YouTube-Chat im Studio:** `YOUTUBE_API_KEY` plus `YOUTUBE_LIVE_CHAT_ID` oder `YOUTUBE_VIDEO_ID`. Setz `YOUTUBE_CHAT_STUDIO_ID` auf das Studio, das ihn zeigen soll.
- **Twitch- und Kick-Chat:** `TWITCH_CHANNEL` und `KICK_CHATROOM_ID`.
- **Anmeldelink im Browser statt im Terminal**, für Tests und `bun run measure`: `CASTHOP_DEV_LOGIN=1`.

## Fehlerbehebung

**`permission denied while trying to connect to the Docker daemon socket`**
Dein Nutzer ist nicht in der Gruppe `docker`. Führ `sudo usermod -aG docker $USER` aus und melde dich ab und wieder an, oder setz `sudo` vor die Docker-Befehle.

**`Port 5173 is already in use`**
Ein anderer Dev-Server läuft schon. Beende ihn, oder such ihn mit `ss -ltnp | grep 5173`. Casthop nimmt keinen anderen Port, weil der Recorder `5173` erwartet.

**Health zeigt `"ok":false`**
LiveKit läuft nicht oder ist nicht erreichbar. Prüfe `docker compose ps` und `docker compose logs livekit`. Port `7880` muss frei sein.

**`Refusing default LiveKit devkey/secret outside local loopback`**
Du hast die App auf einen LiveKit-Server gerichtet, der nicht auf `127.0.0.1` liegt, nutzt aber noch die öffentlichen Testschlüssel. Erzeuge echte Schlüssel (siehe [Self-Hosting](/docs/self-hosting)) und trag sie in `.dev.vars` ein.

**Kein Anmeldelink**
Schau ins Terminal von `bun run dev`, nicht in dein Postfach. Wenn du sehr oft Links angefordert hast, ist die Anmeldung für ein paar Minuten pausiert (alle 15 Minuten: 5 Anfragen pro Netzwerk, 3 Links pro E-Mail).

**Hängt bei Starting**
Egress konnte die Studioseite nicht öffnen oder MediaMTX nicht erreichen. Prüfe `docker compose logs egress`. Stell sicher, dass `bun run dev` noch läuft und `data/recordings` beschreibbar ist.

**Keine Kamera am Rechner**
Casthop weicht auf ein Testbild und stummes Audio aus, so kann auch ein Server oder eine VM beitreten. Du kannst Chrome auch mit `--use-fake-device-for-media-stream` starten.

**Bun warnt wegen der Version**
Führ `bun upgrade` aus. Das Repo erwartet Bun 1.4.5 oder neuer.

## Docker Desktop (macOS und Windows)

Die Compose-Datei nutzt Host-Networking, und das funktioniert nur unter Linux. Unter Docker Desktop:

- entferne `network_mode: host` bei jedem Dienst,
- veröffentliche `127.0.0.1:7880-7882`, `127.0.0.1:1935`, `127.0.0.1:8888`, `127.0.0.1:6379` und `127.0.0.1:9090`,
- setz LiveKits `rtc.node_ip` auf `host.docker.internal`,
- richte Egress-`ws_url` und Redis auf `host.docker.internal`.

Browser-Video auf demselben Rechner kann so trotzdem unzuverlässig sein. Linux ist vorerst der unterstützte Weg.
